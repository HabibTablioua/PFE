\section{Architecture du projet}
L'architecture de ce projet repose sur le modèle des microservices, une approche robuste et évolutive, particulièrement adaptée au traitement des transactions financières conformes à la norme ISO 8583. Cette conception structure l'application en une collection de services indépendants et spécialisés, facilitant la maintenance, assurant une meilleure tolérance aux pannes et permettant des déploiements rapides et flexibles.

\subsection{Composants principaux}

\begin{enumerate}[label=\alph*)]
    \item \textbf{API Gateway} :
    \begin{itemize}[label=\textbullet]
        \item Point d'entrée unique pour les requêtes externes provenant du réseau public
        \item Redirige les appels vers les microservices internes
        \item Applique des politiques de sécurité, de routage et d'authentification JWT
        \item Gère et redirige le trafic vers les microservices appropriés
    \end{itemize}

    \item \textbf{AuthService} :
    \begin{itemize}[label=\textbullet]
        \item Gère les opérations liées aux utilisateurs et l'authentification
        \item Implémente la gestion des rôles (\textit{Admin/Testeur}) avec JWT
        \item Connecté à sa base de données MySQL pour la persistance des utilisateurs
        \item Fournit la sécurité centralisée pour tous les microservices
    \end{itemize}

    \item \textbf{PackingISOService} :
    \begin{itemize}[label=\textbullet]
        \item Responsable de la génération et du formatage des messages ISO 8583
        \item Traite les 49 champs de données selon le standard international
        \item Envoie les messages générés vers ResponseISOService via RestTemplate
        \item Connecté à sa base de données MySQL pour l'historique des générations
    \end{itemize}

    \item \textbf{DepackingISOService} :
    \begin{itemize}[label=\textbullet]
        \item Analyse et décompose les messages ISO 8583 reçus
        \item Détecte automatiquement le format (ASCII ou HEX) des messages
        \item Masque les données sensibles (PAN, Track Data) pour la sécurité
        \item Envoie les résultats d'analyse vers NotificationService
    \end{itemize}

    \item \textbf{ResponseISOService} :
    \begin{itemize}[label=\textbullet]
        \item Traite et gère les réponses aux messages ISO
        \item Stocke les statuts des transactions (\textit{SUCCESS/FAILED})
        \item Envoie des notifications vers NotificationService
        \item Connecté à sa base de données MySQL pour la persistance des réponses
    \end{itemize}

    \item \textbf{TransactionHistoryService} :
    \begin{itemize}[label=\textbullet]
        \item Gère l'historique complet des transactions traitées
        \item Fournit les données pour les tableaux de bord et rapports
        \item Centralise les métriques de performance du système
        \item Connecté à sa base de données MySQL pour l'archivage
    \end{itemize}

    \item \textbf{IncidentReportService} :
    \begin{itemize}[label=\textbullet]
        \item Gère la déclaration, le suivi et la résolution des incidents
        \item Détecte automatiquement les causes d'échec des transactions
        \item Propose des solutions appropriées pour chaque type d'incident
        \item Envoie des notifications d'incident vers NotificationService
    \end{itemize}

    \item \textbf{MonitoringService} :
    \begin{itemize}[label=\textbullet]
        \item Collecte et analyse les logs de tous les microservices
        \item Fournit une vue centralisée de l'état du système
        \item Permet le filtrage et la recherche dans les logs
        \item Connecté à sa base de données MySQL pour la persistance des logs
    \end{itemize}

    \item \textbf{NotificationService} :
    \begin{itemize}[label=\textbullet]
        \item Service centralisé pour l'envoi de notifications
        \item Reçoit les demandes de notification de tous les microservices
        \item Gère l'envoi d'emails aux administrateurs
        \item Connecté à sa base de données MySQL pour l'historique des notifications
    \end{itemize}

    \item \textbf{Serveur de découverte (Eureka)} :
    \begin{itemize}[label=\textbullet]
        \item Permet aux microservices de s'enregistrer et de se découvrir dynamiquement
        \item Gère la découverte automatique des services dans l'architecture
        \item Facilite la communication inter-services sans configuration statique
    \end{itemize}
\end{enumerate}

\subsection{Base de Données}
Chaque microservice dispose de sa propre base de données MySQL, garantissant :
\begin{itemize}[label=\textbullet]
    \item L'indépendance des données entre services
    \item La scalabilité horizontale de chaque service
    \item La résilience en cas de panne d'un service
\end{itemize}

Cette architecture microservices offre une solution robuste, scalable et maintenable pour la simulation des transactions financières ISO 8583, avec une séparation claire des responsabilités et une communication efficace entre les composants.

\section{Architectures : monolithique vs microservices}
L'architecture logicielle peut être conçue selon différents paradigmes. Les deux approches les plus courantes sont l'architecture monolithique et l'architecture microservices. Chacune présente des avantages et des inconvénients selon le contexte et les besoins de l'application.

\textbf{Architecture Monolithique} & \textbf{Architecture Microservices} \\
\hline
Une seule application regroupant tous les modules & Application composée de plusieurs services indépendants \\
\hline
Déploiement unique & Déploiement indépendant de chaque service \\
\hline
Difficulté de mise à l'échelle sélective & Scalabilité fine selon les besoins de chaque service \\

L'image ci-dessus offre une représentation visuelle claire et pédagogique des deux grandes approches architecturales utilisées dans le développement d'applications : l'architecture \textbf{monolithique} (à gauche) et l'architecture \textbf{microservices} (à droite).

\paragraph*{Architecture Monolithique} 
Dans ce modèle traditionnel, l'ensemble des composants de l'application — \textit{interface utilisateur}, \textit{logique métier}, et \textit{couche d'accès aux données} — sont étroitement intégrés au sein d'un même bloc logiciel. L'application repose sur une base de données unique, partagée entre tous les modules. Cette architecture présente l'avantage d'être simple à développer et à déployer dans les premières phases du projet. Toutefois, elle présente plusieurs limites à mesure que l'application évolue : difficulté de mise à l'échelle, faible résilience, déploiement global en cas de modification mineure, et complexité de maintenance \cite{martin-fowler-microservices}.

\paragraph*{Architecture Microservices}
À l'inverse, l'architecture microservices adopte une approche distribuée. Chaque fonctionnalité de l'application est encapsulée dans un microservice indépendant, doté de sa propre base de données et capable de communiquer avec les autres via des interfaces bien définies (souvent des API REST). L'interface utilisateur centralise les échanges avec les différents services. Cette modularité offre de nombreux avantages : meilleure scalabilité, facilité de maintenance, indépendance des équipes de développement, et possibilité de déploiements continus \cite{martin-fowler-microservices}.

Spring Security est un framework puissant utilisé pour sécuriser les applications web et les services REST dans l'écosystème Spring. L'une de ses fonctionnalités clés est l'authentification avec JSON Web Tokens (JWT). Cette méthode d'authentification moderne permet de sécuriser les échanges d'informations entre un client et un serveur en utilisant des jetons cryptographiquement signés. Lorsqu'un utilisateur se connecte avec succès, le serveur génère un JWT contenant des données d'identification et de rôles. Ce jeton est ensuite envoyé au client qui l'inclut dans les en-têtes de chaque requête ultérieure. Le serveur peut ainsi vérifier l'intégrité du jeton et autoriser l'accès en fonction des informations qu'il contient. L'utilisation de JWT avec Spring Security offre une méthode robuste et efficace pour gérer l'authentification et l'autorisation, améliorant ainsi la sécurité globale des applications \cite{sprsec}.

\subsection{Traitement du protocole à simuler : le Framework \texttt{JPOS}}

\texttt{JPOS} est un framework open-source, conçu pour des systèmes d'entreprise critiques, qui implémente la norme ISO pour les messages de transactions par carte, notamment les protocoles \textbf{ISO-8583} et \textbf{ISO-20022} \cite{jpos}.

Cette norme internationale définit :
\begin{itemize}[label=\textbullet]
    \item une interface commune permettant l'échange de messages de transaction financière entre acquéreurs et émetteurs de cartes ;
    \item la structure des messages, le format et le contenu des éléments de données ;
    \item ainsi que les valeurs possibles de ces éléments.
\end{itemize}

Basé sur la plateforme Java, \texttt{JPOS} fournit un pont logiciel entre les messages structurés selon la norme ISO 8583 et les systèmes internes de traitement des institutions financières. Il constitue ainsi une base de messagerie essentielle pour les systèmes qui traitent des transactions électroniques réalisées via des cartes de paiement.

Que l'organisation traite des millions de transactions par jour ou quelques dizaines de milliers, \texttt{JPOS} peut être mis en œuvre pour concevoir une solution financière fiable, performante et capable de documenter précisément toutes les données liées aux transactions. Néanmoins, l'intégration de \texttt{JPOS} au sein d'un système existant peut représenter un effort de développement conséquent pour assurer une mise en œuvre efficace et fluide.

\textbf{Dans notre projet}, nous avons fait le choix d'utiliser \texttt{JPOS} plutôt que de coder manuellement le traitement des messages ISO, car il s'agit du seul framework open-source spécialisé dans la gestion complète des protocoles \textbf{ISO 8583} et \textbf{ISO 20022}. Ce choix nous a permis de \textbf{gagner un temps précieux} tout en garantissant une conformité stricte aux spécifications du protocole \cite{jpos}.
